# 知识库内容生成标准 v0.1（草案）

> 目标：进库的东西「以后能被直接讲给一个编程小白」，而且**每一句都能回到原文**。
> 标准分两层：**入库标准**（KB 能收）和 **成卡标准**（能变成会弹给你的教学卡）。

---

## 0. 一条知识的完整形状

```jsonc
{
  "title": "关窗口不等于关进程",          // ≤18 字，不写项目名/端口/函数名
  "text": "窗口只是界面……",              // 80–400 字，人话，含一个真实场景
  "summary": "界面退了，进程可能还在跑",   // 只写 1 句，不按字数卡
  "source": {
    "project": "示例项目",
    "session": "session-4a8b42f1",
    "quote": "关窗口不等于关进程",         // 必须逐字出现在原文
    "anchor": "turn=12;seq=418..421"
  },
  "tags": ["端口", "进程"],               // 2–5 个
  "lane": "mechanism",                    // mechanism|syntax|algorithm|judgment
  "confidence": "A",                      // A 可核验 / B 有引文未复现 / C 推断
  "createdAt": 1794130000000
}
```

---

## 1. 入库标准（硬门槛，缺一不进）

| # | 要求 | 判定方式 |
|---|---|---|
| 1 | **有原文引文**，且能在会话原文中**逐字命中**（去空白后子串匹配） | 代码校验，失败直接拒 |
| 2 | 有来源锚点：项目 + 会话 + turn/seq 区间 | 至少 session + quote |
| 3 | 标题 ≤18 字，不含项目名、端口号、函数名、文件名 | 正则 + 人工抽查 |
| 4 | 正文 80–400 字，**没有未解释的术语**（术语表里没有的词要么解释要么删） | 模型判 + 抽查 |
| 5 | 能写出一句「所以」：以后看到 X，先想到 Y | 必须有，否则不成立 |
| 6 | 不是纯操作说明（安装/启动/改配置）——除非它带判断（「为什么先做 A 再做 B」） | 人工判 |
| 7 | 不含凭证、token、个人隐私路径、原始日志整段 | 正则拦截 |
| 8 | 不与库内已有条目重复（同概念同角度） | 相似度 >0.9 合并 |

> 第 1 条是**唯一防幻觉闸门**，和现有卡片入库规则一致；宁可少收，不可编。

---

## 2. 可信度分级

| 级别 | 定义 | 用途 |
|---|---|---|
| **A** | 有逐字引文 + 事后复现过（同一现象再出现 / 修好了验证过） | 可以成卡、可以直接弹 |
| **B** | 有逐字引文，但只出现过一次、没复现 | 可以成卡，只出角标 |
| **C** | 模型推断/经验总结，无原文 | **只进 KB 候选，不成卡、不弹** |

建议：`C` 单独放一个 `candidates/` 区，攒够 3 条同主题再人工复核升 B。

---

## 3. 去重与合并

- **判重键**：`概念 + 角度`（不是标题字面）。角度指「讲的是机制 / 语法 / 坑 / 判断」。
- 相似度 >0.9 → 合并：保留旧条目，追加新引文，`updatedAt` 取新，`confidence` 取高。
- 同一概念最多 3 个角度；超过就说明该合并成一张卡的多面，而不是多条知识。
- 合并时**不要丢旧引文**——它是“这条知识被多次验证”的证据。

---

## 4. 成卡标准（KB → 会弹的卡）

在入库标准之上再加四条：

1. **有比喻**（≤50 字，生活场景）；
2. **有图**（只证一个关系，删掉图还读得懂就说明不需要图）；
3. **有边界题**（什么情况下这条不成立）；
4. **有变式题 ≥1 道**（识别/因果/应用任一），且选项含「我不知道」。

> 也就是说：**KB 收“知识”，卡片是“教案”**。KB 里 100 条，能成卡的可能只有 20 条，这正常。

---

## 5. 禁止入库清单

- 密码、token、cookie、私钥、完整个人路径；
- 整段原始日志、堆栈（只留能说明问题的那 1–3 行）；
- 一次性的数值（端口号、某个文件的第几行）——它们不是知识；
- 没有来源的“最佳实践”“建议”（除非有你自己的原文依据）；
- 空话：要细心、要注意、多测试、保持简洁；
- 与用户项目无关的通用教程摘抄（那是搜索引擎的活）。

---

## 6. 可执行校验清单（写进 KB 写入前）

```
□ quote 在原文中逐字存在（去空白比对）
□ session 存在且 quote 属于该 session
□ title ≤18 字且不含项目名/端口/函数名
□ text 80–400 字
□ 有 takeaway（所以句）
□ tags 2–5 个、lane 合法
□ 无凭证/隐私正则命中
□ 与库内相似度 ≤0.9，否则走 merge
□ confidence ∈ {A,B,C}；C 只进候选区
```

任何一条不过：**拒收并写原因**，不要静默丢弃（方便你看是哪类内容总在失败）。

---

## 7. 入库节奏建议

- **实时**：只收「A 级 + 有逐字引文」的，一次 1 条，避免灌水；
- **离线**：每晚把当天候选批量过一遍标准，合并去重后再入；
- **每周复盘**：看 `confidence=C` 的条目有没有被后续验证升 B，没有就清掉。
---

## 8. 标签规则（2026-11-13 新增）

1. **生成时自带标签**：每条知识必须给 2–5 个标签，不能留空；
2. **入库前遍历现有词表**：从 `tools/tag-map.json` 的 `canon`（当前 56 个受控标签）里选，**能用现成的就不要造新词**；
3. 确实没有合适的才新增，并同时补进词表；禁止同义新词（mac/Mac/macOS、报错/错误处理、状态一致性/状态管理 都只留一个）；
4. 生成阶段由提示词给出词表，入库校验再映射一次；以后这一步交给本地 LLM 做（它擅长批量归类，但也要过同一张词表）。
