# 多维度学习：四条线，不是四门课

> 回应你的问题：「是不是可以做多维度学习，比如语法、算法、机制等」。
> 答案：可以，但只有一种做法不会死——**按"你当时的问句"分线，不按课表分线**。
> 这篇只讲这件事，其他设计见 `设计对话-v0.1.md`。

---

## 0. 先说清楚你现在的位置

你自己给的描述很准，我原样记下来：

> 目标读者：能通过 AI 的思考流程理解意图，但不熟悉代码和算法；要的是看懂、判断、验收，不是独立写程序。

这句话其实定义了三条边界，后面所有设计都从它出发：

1. **你能读"意图"，读不了"实现"** —— 所以语法线不是从零教编程，是**把意图和那行代码接上**。
2. **你对机制有兴趣、但只到"听说过"** —— 所以机制线不需要从"什么是电脑"开始，从"你以为你懂、其实差一层"的地方切进去。
3. **你的目标不是"能独立写程序"** —— 是**看懂、判断、验收**。这个目标必须写死，否则四条线会一起膨胀成"计算机专业四年课程"。

---

## 1. 为什么不能按课表分线

你原来的痛点原话是：「专门的课程与实际的开发存在距离，小白不能很好的衔接构建逻辑关系」。

如果四条线变成"语法课 / 算法课 / 机制课 / 工程课"，那你就是**又给自己报了一个需要系统学完的课程**——回到你已经失败过一次的那条路（没时间、没顺序、学完用不上）。

所以分线的依据不能是"学科"，只能是**你当时卡住时问的那句话**：

| 你当时问的 | 进哪条线 | 这条线要给你的 |
|---|---|---|
| 「为什么会这样？」 | **机制** | 判断方向：先看哪里 |
| 「这行代码在干嘛？」 | **语法** | 读出意图：它在做什么 |
| 「这么做会不会慢 / 会不会崩？」 | **算法** | 判断代价：值不值 |
| 「该选哪个？算做完了吗？」 | **判断（工程）** | 做决定、验收 |

**同一次现场只会进一条线。** 因为你在那一刻只会问一个问题。这是"多维度"不变成"四倍负担"的唯一办法。

---

## 2. 四条线各自长什么样

| | 机制 | 语法 | 算法 | 判断 |
|---|---|---|---|---|
| **你在问** | 为什么会这样 | 这行在干嘛 | 会不会慢/崩 | 该选哪个 |
| **目标能力** | 能判断方向 | 能读出意图 | 能判断代价 | 能做决定并验收 |
| **不要求** | 背定义 | 从零写出来 | 推导复杂度 | 记住所有方案 |
| **素材从哪来** | 报错、现象、设计决策 | **你自己项目里的那几行代码** | agent 说"这里会卡""这里 O(n²)" | 你做过的选择、验收口径 |
| **卡面问题形态** | 二选一因果 / 先看哪 | 给 3 行代码：这行在做什么 | 两个做法：哪个更慢/更险 | 两个方案 + 代价 |
| **图型** | 时序 / 状态机 / 层级 | 代码标注（高亮 1 行） | 时间轴 / 预算条 | 并排对比 |
| **怎么算"会了"** | 能说出因果链 | 能指着它说"这是入口" | 能预判哪里会卡 | 能说出为什么不选另一个 |
| **典型卡** | 为什么改了代码要重启 | `const app = express()` 在干嘛 | 为什么改一下要等三秒 | 这个功能算做完了吗 |

注意最后一列和倒数第二列：**四条线共用同一套卡片结构**（卡面问题 → 背面比喻 → 术语 → 所以句 → 来源），只是问题形态和图型不同。所以你不需要学四个产品，只有一个产品，四个抽屉。

## 3. 语法线：唯一必须"贴着你自己的代码"教的一条线

这条线最容易做错。做错的方式是：出一张卡叫「什么是变量」，讲一段定义。

**错在哪**：定义是通用的，而你的问题是具体的——打开 `app.js` 看到 200 行，不知道从哪看起。通用定义解决不了这个。

**最有效的卡形，可能不是「这行在干嘛」，而是「意图 → 代码行」。**

因为你有一个别人没有的优势：你能读懂 agent 的思考流程，知道它"想干什么"。那就把这个能力直接接到代码上——

> agent 说：「我给请求加一个失败重试。」
> 它改了 3 行：
> ```
> 12  const res = await fetch(url);
> 13  if (!res.ok) throw new Error(res.status);
> +14  for (let i = 0; i < 3; i++) { ... }
> ```
> 问：哪一行在做"重试"？为什么是它，不是上面两行？

这比"什么是循环"有效十倍，因为它用你已经会的东西（读意图）去换你还不会的东西（读代码）。

具体做法还是三步：

1. **先建"代码地图"**：把每个项目里被改得最多的 2–3 个文件挑出来（比如 example-project 的 `app.js`，被反复改动），它就是你的教材。
2. **每张卡只取 3–6 行**，而且必须是**你真见过、且它当时起了作用**的那几行。
3. **目标分三个台阶，到第二台阶就算达标**：
   - `认得`：这行在做什么（`const app = express()` → 把工具箱拿过来，起名叫 app）
   - `说得出`：为什么这么写（为什么先 `express()` 再 `app.get()`）
   - `能改一处`：改一个数、改一个条件、加一行日志——**只改，不写新的**

第三台阶刻意设得很低。因为你的目标不是"会写"，是"能验证 agent 写的对不对"。

## 4. 算法线：只讲你项目里真的会卡的那三种

不要讲排序、链表、二叉树——那些你三年也用不上，讲了就是课程。

你项目里真正会遇到的只有三种，而且都能用图讲：

1. **循环里做重活**（每次都要把所有人重新算一遍 → 人一多就卡）→ 图：时间轴随人数变长
2. **每帧都跑**（界面每秒画 60 次，每次都在算同一件事）→ 图：预算条被塞满
3. **一次读太多**（把整个文件/整张表读进内存）→ 图：内存条被占满

这三张卡讲完，你就能听懂 agent 说的"这里 O(n²)""这个会爆栈""这里每帧都在重算"——**听懂，就是这条线的终点**。

## 5. 判断线：你其实已经很强，但缺一套口径

你在日志里 11 次要求"梳理/复盘/指标表"，说明你天然在管"这摊事的状态"。这条线不是教你判断，是**给你一套可复用的判断清单**：

- 验收：断网会怎样 / 数据空会怎样 / 连点两下会怎样（三次里至少一次能抓到真 bug）
- 取舍：两个方案的代价各写一行，选不出来就说明还缺一个约束
- 降级：备用路径必须让人看见（这条踩过——某次静默降级）

这条线的卡片最少（一个月 3–5 张就够），但每张价值最高，因为它直接省你的返工。

## 6. 防"四倍负担"的四条硬规矩

多维度最怕的是四倍卡片、四倍焦虑。定死四条：

1. **一次现场只出一条线的卡。** 其余三条线如果也值得讲，进"待讲队列"，不当天发。
2. **每日 ≤3 张的总预算不变**，按"最近哪条线的卡点最多"动态分配，**不做平均配额**。可能一整周都是机制，也可能某天连出两张语法——由你的现场决定，不由课表决定。
3. **每条线独立算掌握度**。你在机制上是 L2，在语法上是 L0，这是正常状态，不是"落后"。不显示总分、不显示"完成度"。
4. **线之间用边连起来**。同一个现场的两条线卡片，用 `同源` 边连（机制卡 ↔ 语法卡）；语法卡可以 `前置` 于算法卡（不懂那行在干嘛，就判断不了它慢不慢）。这样四条线最后会在概念图上汇成一张网，而不是四个平行的抽屉。

## 7. 调度：先两条，后四条

你选了「两周考古 + 卡片站」。四条线不用同时开，按这个顺序：

| 时间 | 跑哪条线 | 为什么 |
|---|---|---|
| **W1** | 机制 + 语法 | 你缺的正好是这两块：一个解释"为什么会这样"，一个解释"这行在干嘛"；素材密度也最高 |
| **W2** | 加 算法 + 判断 | 同一批日志重扫，只换"取素材的规则"和"讲法模板"，成本很低 |
| **W3** | 概念层 | 四条线开始汇到同一批概念上（比如"启动时读一次 vs 每次读"同时是机制和算法） |
| **W4** | 入口（待定） | 这一步涉及插件，等卡片质量验证完再谈 |

**W1 的验收线**（不达标就停）：抽 10 张（机制 5 张、语法 5 张），你至少 8 张觉得"这个我确实没完全搞懂"。语法卡另加一条：5 张里至少 3 张你能不看答案说出"这行在干嘛"。

语法线和算法线在 W2 加，是因为它们的素材不用重新扫日志——**同一批会话里，`tool/call` 的 `edit` 参数就是你的代码改动记录**（比如 app.js 被反复改动）。换的只是"取素材的规则"和"讲法模板"，成本比想象中低。

## 8. 一个真实例子：同一段现场，四条线四种讲法

现场：你改完代码、刷新没变。

> 这一段在原型里有可切换的版本（`prototype/index.html` 第 ③ 屏）。

**机制 · L1｜为什么改了代码要重启**
程序启动时把代码读进内存，之后一直用内存里那份。你改的是硬盘上的文件，它读的是内存里的旧版本。所以"重启"= 让它重新读一遍硬盘。

**语法 · L0｜`const app = express()` 在干嘛**
`const` = 给下面这个值起个名字、以后不改它；`express()` = 叫来一个现成的工具箱；`app` = 你给这个工具箱起的名字。整句：把工具箱拿过来，名字叫 app。以后所有 `app.xxx` 都是在跟这个工具箱说话。

**算法 · L1｜为什么改一下要等三秒**
它每次都把"启动流程"从头跑一遍，连没变的文件也重新读、重新编译。所以你改一行和改一百行，耗时差不多——代价不在改动量，在"整体重跑"。这就解释了两件事：为什么热更新快、为什么它有时不生效（它只换了运行时那部分）。

**判断 · L3｜这个功能算做完了吗**
"能跑"不等于"做完"。三个问题：断网会怎样、数据空会怎样、连点两下会怎样。答不全，就还是没做完。

四条线讲的是同一件事，但**你拿走的判断能力不一样**：判断方向 / 读懂代码 / 预判代价 / 决定是否收工。

## 9. 这篇新引出的一个需要你确认的问题

语法线要不要"读代码"这个动作？也就是卡面直接给你 3 行代码，问你"这行在做什么"（4 个选项）。

- **要**：这是语法线唯一有效的形式，但需要多做一个"代码地图"（把项目文件切块、挑出高频修改的片段），W2 的工作量会多 3–5 天。
- **不要**：只做"文字讲代码"的卡片（给你看代码 + 讲明白，不出题），省时间，但大概率退化成"看过了"。

我的建议：**要**，但第一版只做 1 个项目、1 个文件、10 张卡，先验证你愿不愿意答题。
